# 技术架构研究方案

状态：方案，尚未实现或证明可行。不得将架构目标描述为已验证游戏接口。

## 运行模型

以多个隔离的个人爬塔状态，共享一场比赛管理状态为目标，而非仅取消地图投票。个人房间、战斗行动、随机数、奖励与幕进度分别归属玩家。比赛管理处理身份、首杀、通关、跨玩家交易、护盾和净化。

优先复用游戏生命周期、命令与 MOD 内容模型；社区 BaseLib 可以作为候选依赖，最终版本与是否必须依赖尚未确定。必要运行时补丁仅随 MOD 加载启用，不改写原版磁盘文件。

## 模块职责

| 模块 | 职责 |
| --- | --- |
| Match | 房间规则、身份、模式版本、事件顺序、首杀与排名 |
| PersonalRun | 独立路线、牌组、遗物、房间、幕与随机流 |
| CombatIsolation | 敌人、行动队列、回合时机、效果作用域 |
| Effects | 29 项内容、强化、期限、预算与历史计数 |
| Transactions | 献祭、领取、净化、汲取和反击的唯一结算 |
| SyncAndRecovery | 快照、断线恢复、去重、状态核对 |
| Presentation | 正式术语、候选说明、负担、风险与公开进度 |
| Distribution | 包标识、版本、资源、依赖与兼容检查 |

所有影响玩法的状态具有比赛、玩家、房间和事件归属。当前活动效果与历史取得计数分离，不能用显示名称作为持久标识。牌组原卡身份、耐久和升级单独保存。跨玩家衍生事件记录原始来源与是否可继续传播。

## 一致性要求

献祭奖励作废与效果授予必须是同一笔可恢复交易。每个客户端重发或断线恢复均不得复制奖励、伤害、金币、反击、次数或首杀。房主统一确认比赛结果与跨玩家交易；个人战斗究竟采用重放、房主模拟或其他验证方式尚待研究，不能只相信客户端上报“胜利”。

随机流按玩家、幕、节点与用途隔离。候选、负担快照、回合伤害骰子和原牌变化结果应能恢复，菜单操作不重抽。公开进度不携带对手隐藏牌组和遗物明细。

研究重点包括：房间和战斗单例、全员等待栅栏、多人消息默认作用域、单一共享存档假设、多人专属机制以及本机 v0.111.0 的实际接口。

## 验证目标

未来验证完整模式：玩家在不同节点与不同幕同时推进；同节点独立遭遇；单人怪物规则；跨幕延迟攻击；护盾和净化；叠加与奖励补偿；三个献祭渠道；复活与免死；断线恢复；冠军锁定；本地和工坊加载一致。

测试顺序可以按技术依赖安排，但最终交付范围保持完整，不能将验证阶段误写为缩减版产品承诺。
