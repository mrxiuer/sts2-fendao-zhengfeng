# 原版保存流程核对与优化依据

核对对象：当前本机 sts2.dll 的 RunManager、CombatManager、EventRoom、SaveManager、RunSaveManager 反编译结果。

## 原版实际时机

- `RunManager.EnterMapCoord` 添加已访问坐标，再以 `saveGame:true` 进入 `EnterMapPointInternal`。退出旧房间、清理界面和同步后，调用 `SaveManager.SaveRun(null)`，随后创建新房间。
- `CombatManager` 胜利流程先完成战斗结束与胜利钩子，再 `room.MarkPreFinished()`，调用 `SaveManager.SaveRun(room, saveProgress:false)`。因此不是整场只有进入节点一次保存；胜利后的房间也有存档。
- `EventRoom.OnEventStateChanged` 对 AncientEventModel 检查所有玩家事件完成后，标记完成并保存；不能泛化为每个事件、每次点击均保存。
- `SaveManager.SaveRun` 等待上一存档任务并使用 BeginSaveBatch；RunSaveManager 仅在 ShouldSave 且本地为单人或房主时写当前局文件，常规使用异步序列化与写入。
- 暂停菜单 `NPauseMenu.CloseToMenu` 的“保存并退出”只执行返回主菜单；`NGame.LoadMainMenu` 等待已有 CurrentRunSaveTask 完成，没有在按钮路径新建每项操作存档。
- `RunManager.ToSave` 保存随机数状态、概率状态、遗物池、玩家、地图、房间与进度，固定种子不是完整的恢复数据。`LoadIntoLatestMapCoord` 使用 `saveGame:false` 进入已保存坐标，避免读档本身再次覆盖存档。

## 模组目前额外负担

- 节点、胜利、单项奖励和多种主动操作都会调用个人 Checkpoint。
- RaceRecovery 每三秒采集并发送恢复快照，包含原生局与奖励状态。
- 每条成功比赛命令发布完整 Match，完整历史命令、公开牌组等都被重复传输；后台写盘并不能消除同步、压缩和网络成本。
- 原版关键阶段保存值得沿用，但独立进度、跨玩家干扰/交易与奖励领取凭证仍要保留；不能仅保留种子，也不能将原版共享战斗的单份存档直接替代各玩家的独立局。

## 实施原则

完整快照以房间关键阶段为主；房主主动保存仍收集在线玩家最新安全状态，掉线玩家使用已有快照与未应用凭证。普通动作使用必要变更记录，合并相同快照与重复落盘，不每次重发全历史。读档继续保留已领取奖励、买牌双边交接、营地/商店操作与战斗从头开始的语义。每项生产改动需回归对应的中间状态恢复，不以减少存档次数换取重复领奖或状态错位。

## 已落地的本地改动与验收状态

战后检查点已从 `RaceModifier.AfterCombatVictory` 移到原版 `SaveManager.SaveRun(completedRoom)` 完成后；这样采集时房间已被标记完成，避免提前采集和重复的战后钩子检查点。进房保存仍在 AfterRoomEntered 应用开场效果后执行，不能把原版创建房间前的保存直接当作模组开场效果已经交付的证据。

比赛状态传输新增 `state_delta`：首次握手、同修订调试改动、变化过大或同步修复发送完整状态；正常命令发送精确字段增量。递增集合只发送新增尾部，删项/替换/数组重排按完整语义编码；包含比赛身份、规则、前后修订和两端SHA256校验。基线失配不提交部分状态，不确认命令，客机请求完整状态后继续；原有完整Match落盘和恢复归档不改成增量链。握手增加wire:1，避免旧二进制误接受不支持的新消息。

核心新增四组检查（89项总检查通过）：完整历史、字典删除、空值与数组修改；80步连续变更；错误身份/修订/路径/数组类型及损坏校验拒绝。第一版增量四进程原生奖励通过，第二轮又验证三个客机人为丢失基线均请求完整状态、完成原命令，检查落盘全历史仍在；RewardRecovery双方新局及归档重启、Network真实收入/分享均通过。进一步减少编码重复解析和对齐原版战后存档后的新构建仍在进行定向回归，不把前一构建结果当作最终验收。

三秒备份目前未从生产路径删除：单独关闭它不足以治好延迟，且事件/商店中间变化仍需恢复保障。后续只在对应变更记录和恢复测试覆盖后合并/减少冗余备份，不直接拿种子替代恢复记录。


测试收尾另发现原生 ENetClient.DisconnectFromHost 在 Flush 后立即 Destroy，退出通知使用非可靠标志8；本地压测偶发出现客机已成功退出但房主仍保留连接。性能夹具现改为先用原始ENetPeer.PeerDisconnectLater完成可靠传输断开，再销毁测试连接，房主继续以真实断开事件为完成依据；不把退出握手超时当作通过，不改生产游戏的原生连接实现。此夹具修复正在四进程重测。


## 图标冷加载与可靠收尾的后续结果

进一步核对发现原始图标1254×1254，旧EffectIcons.Get在第一次展示时同步解码并Lanczos缩至128×128；这与存档次数无关，却直接位于候选弹出路径。Build-IconTextures.ps1现使用独立Godot工程预生成67张显示纹理，每张保存/重载后逐字节比较RGBA8像素与原运行时缩放结果，原始美术不删不改；构建检查源文件与显示缓存双方SHA256以防旧缓存。DLL从123830272降至13462016字节，运行时只加载小纹理，避免领奖时执行大图解码/缩放。90项核心检查与原生Single通过（包括全部图标加载）。新包的四进程选牌专项与恢复仍在运行。

可靠收尾最终还必须包含原生ENetDisconnection应用退出报文：ENetHost仅凭裸ENet断开不会移除其应用玩家列表。夹具发送该报文时使用可靠标志1，双端继续服务ENet直到实际Disconnected，房主同时等待应用列表和底层连接均结束。修正后四进程12轮金币奖励与全员退出均实际通过；客户端36个样本按比较脚本分位定义中位数66.8ms、P95约85.7ms、最慢86.1ms。此构建574/578次广播为增量，编码内容429544字节（未乘接收人数，不含原生与恢复消息）。先前仅使用PeerDisconnectLater的失败日志不计通过。


最新完成状态：小纹理构建的四进程奖励与可靠收尾均通过，三客机失配修复及完整落盘历史通过；RewardRecovery新局与双方重启通过。献祭候选P95降至108.5ms。卡牌提交P95为135.5ms但对既有参考基线的相对门槛仍未通过，需最新同构A/B继续验收；不据此标记全部性能或最终交付完成。当前核心检查90项。


## 当前性能验收口径（2026-10-23）

用户明确接受几十毫秒的等待，后续不再以相对提升百分比阻塞交付。保留历史失败与全部慢样本，当前比较器以实际P95上限验收：金币提交150ms、其他领取/刷新提交250ms、菜单打开100ms、献祭候选150ms。最新四进程卡牌/遗物/献祭/Boss选项及药水/各类刷新已通过相应绝对门槛，详见CHOICE-REWARD-PERFORMANCE与REFRESH-REWARD-PERFORMANCE；旧章节中的相对门槛待办由本节更新，不改写旧轮次结果。继续把工作集中于明显卡顿和恢复一致性，不为几十毫秒差距反复改动生产逻辑。

保存失败回归也已通过真实文件锁故障、继续在线补交、再次保存与双方新进程恢复，详见RECOVERY。当前构建91项核心检查通过，最终All尚未完成。
