# 主菜单恢复黑屏修复与胜利结算调查

2026-10-24，基于 GitHub `2ab0f25`（0.5.2）与本机 public-beta v0.111.0 核验。本轮提交源码到 GitHub，未上传创意工坊。

## 恢复黑屏：已修复

角色选择界面开始联机前会调用 `NTransition.FadeOut`。分道争锋的恢复分支调用 `NGame.LoadRun` 恢复场景后直接返回，遗漏了原生主菜单继续游戏在读档之后调用的 `NTransition.FadeIn`，导致过渡层仍可遮挡画面和输入。部分战斗自身的房间过渡可能碰巧撤掉遮罩，因此不应只用没有预先黑屏的直接读档测试覆盖此流程。

修复在成功载入恢复场景之后显式等待 `game.Transition.FadeIn()`。未修改恢复快照格式、规则版本或奖励提交顺序。

新增 `NativeMenuResumeVerification`：两名玩家分别保存商店、营地，回到主菜单后从房主档恢复。`Verify-Native.ps1 -Suite MenuResume` 运行保存与恢复两阶段；所有恢复测试会模拟角色选择之前的黑屏，再检查过渡结束且鼠标放行。macOS 本轮通过独立游戏副本、内存原版进度、两进程 localhost ENet 调用同一验证入口，没有操控桌面，也没有改动正常存档。

结果：

- 未修复对照构建能触发过渡层断言失败；旧测试未模拟的场景已被覆盖。
- 修复后两端的战斗档恢复通过，保留生命、最大生命、待生效诅咒、奖励凭证和暴击重放序列。
- 修复后商店、营地档恢复通过，两端过渡和输入正常，金币、生命、牌组数量保留。
- Release 构建零警告、零错误；97 项现有规则及翻译检查通过。

商店/营地验证器最初的结束通知可能早于对端注册完成，已改为报告目录中的双端完成标记；之前的测试器超时单独保留，不作为产品失败或最终通过记录。

## 怪物全死却未结算：断线失败处理已修复

`NativeVictoryNetworkVerification` 用普通 `StrikeIronclad` 将敌人清场；保持连接为对照，只在客户端最后一击前断开真实 ENet 连接为故障组。该探针显式调用原生胜负检查，覆盖最终攻击后的结算边界，不宣称自动化覆盖了真实鼠标拖牌或 Steam 多机传输。

下表记录胜利钩子返回或抛错时的状态；修复后的断线客户端随后会显示错误并回到主菜单，未确认胜利仍不发奖。

| 场景 | 敌人全死 | 原生房间已结算 | 模式仍在战斗 | 异常 |
| --- | --- | --- | --- | --- |
| 正常连接房主 | 是 | 是 | 否 | 无 |
| 正常连接客户端 | 是 | 是 | 否 | 无 |
| 客户端断线后的房主 | 是 | 是 | 否 | 无 |
| 最后一击前断线的客户端 | 是 | 否 | 是 | IOException |

故障调用链为 `RaceSession.Submit` → `RaceModifier.AfterCombatVictory` → 原生 `Hook.AfterCombatVictory` → `CombatManager.EndCombatInternal`。通信异常向外抛出后，原生流程未执行房间完成标记和后续奖励流程。提交等待也存在超时异常路径，但本轮只主动注入并验证了断线，没有声称已测试丢包或超时。

因此网络故障确实能触发报告的表象，MOD 的失败处理也存在缺口；没有当时客户端日志，仍不能确认用户那一次的实际触发原因。修复保留房主确认作为发奖前提。对客户端的通信失败或超时，先中断原生结算钩子，再延迟调用原生错误弹窗和返回主菜单流程，避免卡在死亡敌人面前。提示玩家让房主保存比赛并邀请原玩家恢复，不将未确认的胜利直接发奖。

连接仍在但确认超时时，同一个胜利 command ID 会请求完整状态并重试一次；重复进入同一房间的胜利钩子共用同一任务，避免创建第二笔胜利。若恢复失败仍进入上述明确错误流程。本轮不增加自动重连；持续断线无法正常提交胜利，须从房主存档恢复。

更新后的断线回归检查未确认胜利不发奖、客户端回到主菜单、原生错误弹窗出现。正常连接对照保持正常结算。超时重试的传输故障未单独注入，幂等性由既有规则测试覆盖。
