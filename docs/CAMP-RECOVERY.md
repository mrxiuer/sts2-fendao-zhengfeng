# 营地保存与恢复验收

2026-10-22，本地开发版0.5.0，尚未发布。运行 `scripts/Verify-Native.ps1 -Suite ServiceRecovery`；脚本启动四个真实ENet进程，完成前置战斗后分别进入营地，三个客户端掉线，由房主保存四份原生进度，再结束并重启全部进程。`-ResumeOnly` 复用同一房主归档。报告在 `artifacts/verification/network/*-ServiceRecovery*.log`，隔离数据在 `artifacts/verification/ServiceRecovery-suite`。

## 已通过的真实场景

| 玩家 | 保存时状态 | 重启后验证 |
| --- | --- | --- |
| 房主／Ironclad | 250/500生命，持永恒羽毛进营地先治疗，再原生休息；已完成营地 | 保留保存时生命，羽毛与休息均不重复，选项为空，不能再次休息，继续按钮可用。 |
| 2号／Silent | 尚未选择；休息、可升级2张的锻造、铲子挖掘及模式净化 | 精确保留选项顺序、数量与锻造次数；通过实际原生按钮选择并升级两张牌，之后可继续。 |
| 3号／Defect | 已用原生锻造升级两张牌，已完成营地 | 原生卡包与升级数值逐项一致，不多升级，不重新提供选项。 |
| 4号／Necrobinder | 已通过原生营地选项与选择器净化普通诅咒 | 净化结果、服务已用标记和房间身份一致，不重新提供净化或其他营地选项。 |

四人均保留生命、最大生命、金币、永久牌组、胜利数与服务标记，奖励/商店/变牌随机计数不变。四人恢复后均实际离开营地，进入下一战并只增加一次胜利，未卡在同步器等待。四人的前置资源、诅咒与锻造2张是隔离夹具条件，不表示普通游戏初始锻造能升级2张。

选择通过原生NRestSiteButton的完整SelectOption流程，包含选项同步器与原生界面收尾；直接调用同步器不会执行按钮负责的演出和继续按钮更新，不能用那种调用检验实际交互。

## 实现与修复

原版SerializableRoom.FromSerializable不支持RestSite，RestSiteSynchronizer也不保存剩余选项。现在营地快照附加实际选项、SmithCount、最后选择索引、完成标记与模式房间身份。恢复时重建原生选项对象与同步器状态，不调用RestSiteOption.Generate，不重复运行可能消耗随机数或修改其他状态的生成钩子。

实现覆盖当前原生九种选项及本模组净化/修复选项；九种的全部选择分支不等于均已实测，表内为本次实际覆盖。未知第三方选项会明确拒绝捕获，避免把缺失私有状态的备份当作完整保存。

另修复模式净化/修复的自动检查点时序：原先在OnSelect内部写入，此时原版尚未移除已用选项。现在等待ChooseLocalOption提交后写入。测试读取真实后台落盘checkpoint.json中的原生包，确认其营地选项与提交后的状态一致，未保存提交前的旧列表。原生休息和升级也在成功提交后更新检查点。

## 仍待验收

选择尚未完成时的保存、带多次营地行动的部分剩余选项、九种原生选项的全部特殊遗物组合与第三方选项扩展，均不能由本次结果替代。事件页面、嵌套战斗返回、R键、在线共同保存、淘汰状态和后期领奖性能仍是独立收尾项目。

后续增加四人实际持有EternalFeather的全流程，进营地治疗只触发一次，保存/全部进程重启后生命仍与快照一致；四人完整ServiceRecovery已通过。此修复区分已进房快照和进房前共同检查点，避免把正常新节点的遗物收益一并禁用。
