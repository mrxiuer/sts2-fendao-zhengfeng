# 四个真实进程与混合房间存档验收

2026-10-22，本地开发版0.5.0，尚未发布。运行 `scripts/Verify-Native.ps1 -Suite FourPlayers`，由脚本启动房主与三个ENet客户端，落盘后结束四个进程，再从房主归档重启四人。`-ResumeOnly` 重用同一落盘场景；测试归档与预期文件在 `artifacts/verification/FourPlayers-suite`，日志为 `artifacts/verification/network/*-FourPlayers*.log`。

## 已通过

- 共享规则与四人名单。1号房主和3号客户端均用实际choose命令取得七项；2号与4号是未持有对照。四人分别使用Ironclad、Silent、Defect与Necrobinder，角色选择与恢复保持一致。
- 四个原生独立战局分别设置500、600、700、800最大生命，用不同数值识别持有者。两名持有者的傀儡各自承受原生攻击与虚弱，治疗限制只影响持有者；时间线读取真正跨ENet的对手卡包，魅惑使用原生卡牌。
- 两名持有者都刷新实际药水奖励。永久卡授予、刷新次数、傀儡生命与双生的两个真实生命池在进程重启后逐项一致。
- 主机保存时，1号和3号停在未完成的不同战斗，2号停在已领取77金币后的剩余奖励界面，4号停在实际购买卡牌、药水并使用删牌服务后的商店。三个客户端掉线后，由房主单独归档四份原生进度。
- 重启后：未完成战斗从第1回合恢复，遁地只返还本次未完成使用；奖励房间不重打、不重复结算，原选项逐项一致且可以实际领取；商店商品、原生卡牌内容、售价、折扣、售罄、删牌服务状态和金币保持一致，恢复不推进商店随机序列，剩余商品仍可实际购买。
- 售罄卡牌的真实原生槽位不可见且忽略鼠标。测试不绕过隐藏槽位直接调用原版购买失败对白：原版对FailureOutOfStock没有对白分支，该调用与实际交互路径不同。
- 两名战斗玩家分别完成恢复战斗与下一场新战斗，每次只记一次胜利，互不推进其他玩家的房间。
- 故障机器人在首次真实分裂后保留已有球与完整球槽，继续原生Channel成功；双生读档后CrackedCore开场充能成功，再次充能仍显示正确。共享球队列只显示一次，第二具身体不额外复制球槽。
- 修复后完整四职业新局与重启流程均通过，双生原生生命周期专项也通过。

首个节点通过原生EnterMapCoord进入，后续额外战斗与商店用原生EnterRoomDebug构建隔离场景，不能据此替代四人实际分路选点和轨迹验收。初始奖励候选与三次胜利充能前提由隔离夹具预置，不表示七项已经开放正常奖励池。当前仍在PendingDefinitions。四人屏障由房主收集到达并广播放行；客户端消息不会自动转发给其他客户端，不能套用双人的互相确认。

## 商店恢复实现

原版SerializableRoom只支持战斗与事件恢复，也没有商品库存。现在在房主原生快照的商店房间附加自有数据，恢复时仅处理带有本模组标记的商店。直接重建原生MerchantInventory与原生条目，保留原生购买、更新、售罄和服务交互；不重新抽商品、价格或遗物池。卡牌原始/修饰内容、折扣和修饰来源同时保留。普通原版流程没有该标记时仍走原生工厂。

## 尚未证明

四职业各自持有全部新增道具的组合、全部道具强化、R键后混合房间恢复、营地/嵌套事件、在线共同保存与生成/领取中间时序、淘汰/已完成玩家，以及后期多效果大牌组的领奖性能仍需专门验收。此专项不替代原生图形、完整技能覆盖或最终性能门槛。

## 双生与原生球槽的修复

RefreshVisualNode会替换整个NCreature，旧NOrbManager已收到CombatSetUp事件，新管理器错过该事件，因而没有槽位。读档重建双生后CrackedCore调用AddOrbAnim会抛出Sequence contains no matching element，使回合停止。现在重建后按同一PlayerCombatState的OrbQueue容量和现有OrbModel恢复原生槽位与显示，不额外Channel/Evoke，不消耗随机数，也不复制逻辑队列。四人新局和原失败归档均验证了修复，之后完整新局/恢复流程再次通过。

后续四人专项给商店对照玩家实际加入原生MealTicket；进商店治疗后的生命纳入预期，重启时生命与最大生命逐项比较，避免只比较金币/牌组而漏掉重复商店治疗。带餐券的完整四人新局/恢复已通过。
